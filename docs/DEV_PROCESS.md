# easynet 开发流程规范

两套流程：**新增功能** 与 **Debug**。任何一条发布前都必须走完各自的清单。

---

## 一、新增功能流程

### 1. 调研先行（动代码之前）

需求确认后，先查成熟方案，**不直接开写**：

- GitHub 搜索同类实现（`gh search repos` / `gh search code`），重点看：星数、维护状态、许可证、与本项目（Go + Wails + Windows only）的兼容性
- 标准库 / 已有依赖是否已覆盖（本项目现成能力：logx 脱敏、netinfo、drcom、selfupdate 等）
- 本项目内可复用的代码

### 2. 方案评审（先给方案，批准后才运行）

把候选方案写成对比，**必须包含**：

| 项 | 要求 |
|---|---|
| 做法简述 | 一两句话说清怎么实现 |
| 优点 | 直接收益 |
| 缺点 / 风险 | 复杂度、维护成本、坑 |
| **体积变化** | 新增依赖写明库名与预估增量；无新增依赖标注「无新增依赖」 |
| 测试影响 | 要不要新单测、会不会动到现有测试 |

给出推荐项，**等用户选择/批准后才开始实现**。有明显分歧时用 AskUserQuestion 收敛。

### 3. 实现

- 遵循项目现有约定：slog 结构化日志、凭据全链路脱敏（logx.MaskURL）、中文注释解释「为什么」
- 路径红线：一切产物写 `D:\trae工作区`（例外：已做好的正式版本可进 `D:\ops测试`）；Go 命令带 `GOTMPDIR`/`GOCACHE` 指向 D 盘
- 不做需求外的重构和「顺手优化」

### 4. 测试清单（发布前逐项打勾）

```
- [ ] 新增单测已写并通过
- [ ] go test ./... 全绿
- [ ] gofmt -l 干净（CI 会挡）
- [ ] wails build 本地构建成功
- [ ] 真机功能验证（列具体验证点，逐项让用户确认）
```

### 5. 发布内容确认（先给用户审）

- 版本号位置清单（version.go / wails.json / easynet.iss / index.html×2 / README×2 / RELEASE_NOTES）
- 改动文件列表（git diff --stat）
- **发布文案全文**先给用户审阅；安全相关更新必须标亮「强烈建议所有用户更新」

### 6. 发布

用户确认 → commit → tag `vX.Y.Z` → push → CI 全绿（release + ci）→ `gh release view` 核对资产数量与大小 → 汇报结果。

## 二、Debug 流程

### 1. 取证（先证据，后结论）

- 收集：日志原文 / 报错原文 / 复现步骤，不凭印象猜
- 静态可判定 → 读代码定位调用链；需要运行时证据且可复现 → 走 TRAE-debugger 采集
- 结论必须能指到具体代码行或具体日志行

### 2. 根因与修复方案（批准后才改）

- 根因分析：一句话说清「为什么会这样」，附证据引用
- 修复方案（如有多个）：同样写**优缺点、影响面、体积变化**（涉及依赖时）
- 等用户批准再动手

### 3. 最小修复 + 验证

- 只修根因，不扩散改动；**不擅自加防御分支/兜底代码**，除非根因就是缺校验
- 测试清单：
  ```
  - [ ] 复现路径已修复（能复现的场景重跑通过）
  - [ ] 相关单测新增/更新并通过（防回归）
  - [ ] go test ./... 全绿 + gofmt 干净
  - [ ] wails build 成功
  ```

### 4. 确认与发布

同「新增功能」的第 5、6 步：发布内容与文案先审 → 用户确认 → 推送发布。

---

## 通用红线

1. 任何面向公众的文本（发布文案、README 改动）先提交用户审阅
2. 安全相关更新标亮提醒；凭据不得出现在日志/状态/界面任何输出
3. CI（含 gofmt）全绿才允许发布；CI 红了先修再推
4. 版本规则 `0.x.y.z`：x 大功能、y 小功能、z 修复
